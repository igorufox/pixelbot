# Заметки о переносе

*[English version](migration.md)*

Что изменилось между архивами 2014 года и этим репозиторием и почему.

## Откуда взяты исходники

Архивов два, и они разного возраста.

`src.zip` — выгрузка исходников за июнь 2014. `workspace.zip` — рабочая область Eclipse за июль 2014,
и она новее: `ScriptEditor` в ней больше, в `Releaser` развёрнуты импорты со звёздочкой, и — решающее
отличие — из неё удалены пакеты `script/*/js/jre`.

Эти пакеты были написаны под `sun.org.mozilla.javascript.internal`, то есть под Rhino, вшитый внутрь
JDK. Java 8 заменила его на Nashorn, и пакет исчез, а `.classpath` рабочей области выставлен на
`JavaSE-1.8`. Автор уже наткнулся на это и бэкенды убрал. Поэтому репозиторий собран из июльской
рабочей области: июньская выгрузка означала бы воскрешение четырёх пакетов против API, которого
больше нет.

## Переименования

Переименовано всё, что несло старое имя: оба корневых пакета, классы главного окна и загрузчика,
логгер, пространство имён, которое библиотека скриптов отдаёт скриптам, заголовок окна, пути к
ресурсам, узел настроек и jar. Виды капчи назывались по мини-играм, из которых были нарезаны; теперь
это `edge`, `tile`, `texture` и `relic`, и вместе с ними переименованы классы решателей.

В одном из двух корневых пакетов лежал устаревший сериализованный формат элементов. Из кода на него
ничто не ссылается — он читается рефлексивно при импорте старых файлов, — поэтому теперь он живёт
под `pixelbot.legacy`.

Переименование пакетов ломает совместимость Java-сериализации с файлами `.elg` и `.ser`, созданными
более старой сборкой, поскольку имена классов пишутся в поток. Здесь таких файлов нет, так что
вопрос теоретический, но знать об этом стоит, если свои у вас остались.

## Что потребовалось, чтобы собралось

Внутренности JDK, на которые опиралась сборка 2014 года, и чем они заменены:

| Было | Стало | Исчезло в |
| --- | --- | --- |
| `com.sun.awt.AWTUtilities` | `Window.setBackground` / `setShape`, `GraphicsDevice.isWindowTranslucencySupported` | Java 9 |
| `sun.net.www.MimeTable` | локальная таблица content-type в `ScriptEditor` | Java 9 |
| `java.awt.peer.RobotPeer` через рефлексию | `Robot.createScreenCapture` | Java 9 |
| `javax.xml.bind.DatatypeConverter` | `java.util.Base64`, `java.util.HexFormat` | Java 11 |

Изменения на уровне библиотек:

* **Eclipse WST JSDT** давал лексер и форматтер JavaScript для редактора. На Maven Central он никогда
  не публиковался, а проект WTP закрыт. Вместо него взяты аналоги из JDT: API у них идентичны по
  форме, поскольку JSDT форкнут из JDT, а грамматика токенов Java покрывает JavaScript достаточно для
  раскраски. Видимая цена — ключевые слова, которых JDT не знает (`function`, `var`, `let`),
  лексируются как идентификаторы.
* **Apache POI** заменил целочисленные константы `Cell.CELL_TYPE_*` на перечисление `CellType` и убрал
  `setCellType(STRING)` как способ превратить число в строку; теперь это делает `DataFormatter`.
* **Дженерики Swing**: `JComboBox<E>`, `ListCellRenderer<E>`, `DefaultComboBoxModel<E>` и
  `TreeNode.children()`, у которого в Java 9 ужесточили возвращаемый тип.
* У `IErrorHandlingPolicy` из **Eclipse JDT** появился метод `ignoreAllErrors()`.
* Вкопированная в дерево исходников копия `org.apache.commons.net.ntp` заменена настоящей
  зависимостью `commons-net`.

И одно, что проявилось только в рантайме:

* `PixelBotApp` строил свой classloader с `null` в качестве родителя. До модульной системы это
  означало весь `rt.jar`; сегодня bootstrap-загрузчик определяет только `java.base`, `java.desktop` и
  ещё несколько модулей, а `java.compiler` живёт в platform-загрузчике. Swing поднимался нормально, а
  потом встроенный Java-бэкенд падал с `NoClassDefFoundError: javax/tools/ToolProvider`. Теперь
  родитель — `ClassLoader.getPlatformClassLoader()`.

## Баги, найденные попутно

Ни один из них не внесён переносом — все были там изначально.

* **`BaseTreeNode.children()` вызывал сам себя.** `return children();` — любой вызывающий получал
  `StackOverflowError`. Теперь возвращается перечисление по детям узла, с сигнатурой, которой требует
  Java 9.
* **Перебор терял совпадения по весу.** `Algorithm.Result` сравнивался только по весу, а результаты
  собирались в `TreeSet`, поэтому каждая расстановка, набравшая столько же, сколько уже встреченная,
  молча выбрасывалась. Теперь `compareTo` разрешает ничью по самой перестановке, а перебор собирает в
  список.
* **Вырожденная статистика получала лучшую оценку.** Дисперсия и ковариация брались напрямую из
  commons-math, который возвращает `NaN` для выборки меньше двух точек. `(long) NaN` — это `0`, то
  есть наименьший, а значит лучший возможный вес: пустая область побеждала любую настоящую.
  Ковариация на такой выборке вообще бросает исключение, что убивало решение целиком. `MomentStats`
  возвращает для этих случаев 0, а `MomentStatsTest` фиксирует поведение.
* **Деление на непроверенный счётчик.** `calculateMassCenter` делил на количество чернильных пикселей,
  не проверяя его на ноль.
* **Неограниченные проходы.** `CaptchaSolverFactory.parseDescriptor` шёл от краёв изображения в поиске
  цвета разделителя сетки без ограничения, полагаясь на `ArrayIndexOutOfBoundsException` как на
  условие остановки, — а тот потом докладывался как общая ошибка.
* **Ошибка приоритета операций.** `ElementDescriptorBase.getImage()` проверял
  `image == null && width != 0 || height != 0`, что разбирается как `(a && b) || c`, — поэтому
  изображение перерисовывалось при каждом вызове. Исправлено, кэш сбрасывается в `addPixel` и
  `setDimensions`.
* **`null` из `File.listFiles()`.** `SettingsPanel.loadPrefs` обходил его напрямую, поэтому свежая
  установка без каталога `scripts/` падала ещё до открытия окна.
* **Закрытие, которое не могло завершиться.** `windowClosing` закрывал окно только если `savePrefs()`
  вернул true, и не ловил то, что тот бросал, — то есть любая ошибка при сохранении настроек оставляла
  окно, которое невозможно закрыть.
* **`FourDimensionVarianceAlgorithm`** был незаконченным экспериментом. Он строил ковариацию 4×4 из
  двух выборок разной длины, индексируя обе длиной первой, — то есть падал всякий раз, когда длины
  различались; в определителе были переставлены индексы (`D[0][2] = D[3][0]`) и удвоены знаки
  (`- -D[0][1]`); а по смыслу он трактовал две несвязанные выборки как четыре координаты одних и тех
  же точек. На него ничто не ссылалось. Он удалён, а не додуман за автора.

## Оптимизации

* **Кластеризация.** Шумоподавление плиток гоняло DBSCAN из commons-math с `minPts = 0`, то есть
  попросту связные компоненты, за O(n²) по пятнадцати тысячам точек на плитку. `GridClusters` делает
  то же одним проходом системы непересекающихся множеств по фиксированному трафарету: тот же
  результат, работы примерно в четыреста раз меньше. Это была самая большая статья расходов в
  решении — куда больше, чем 720 расстановок, ради которых перебор и существует. См.
  [заметки по капче](captcha.ru.md#производительность).
* **Оценка без холста.** `FastDividedVarianceAlgorithm` выводит результат полосового скорера из
  предвычисленных аддитивных моментов вместо пересборки холста на 87 000 бит 720 раз.
* **Параллельный перебор** и удаление измерительного стенда, который обходил отсортированные
  результаты прямо в боевом пути.
* `Vector` и `Hashtable` уступили место `ArrayList` и `HashMap` в том коде, который затрагивался.

## Логирование

Отладочный вывод шёл в `System.out` и `System.err` прямо из циклов оценки, при том что в проекте была
вполне рабочая подсистема логирования с собственным просмотрщиком. Теперь это логируется через
`java.util.logging` на уровнях `FINE` и `FINEST`, где ему и место. Пустым блокам `catch` на
затронутых путях добавлена строка лога.

В остальной кодовой базе по-прежнему около семидесяти пустых блоков `catch` и столько же вызовов
`printStackTrace`. Они авторские, их не трогали.

## Что удалено

* Все пиксельные шаблоны `.elg` (1009 файлов), `config/travel.cfg` и иконка приложения — всё это
  графика или данные предыдущей цели. Наборы иконок состояний и информации ушли туда же; на них
  ничто не ссылалось.
* Иконки панели инструментов. Они были из отладочного интерфейса Eclipse Platform (это EPL) и как
  минимум ещё из одного набора, происхождение которого установить не удалось. Написать для них
  `NOTICE` означало бы гадать, поэтому они теперь генерируются — `tools/generate_icons.py` является
  единственным источником любой иконки, которую содержит программа.
* `banner.txt`, где лежали адрес форума автора и его ник в Skype.
* Скриптовые бэкенды `js/jre`, как описано выше.
* Метаданные рабочей области Eclipse, `.classpath` и `.project`.

## Что добавлено

* Сборка Maven под Java 21, дающая исполняемый shaded jar.
* Скриптовые бэкенды **GraalJS** и **Nashorn** рядом с Rhino: парсер, инстанциатор и мост скоупа для
  каждого, зарегистрированные через существующие сервисные файлы. Чтобы их добавить, не потребовалось
  менять программу — и это лучшее свидетельство того, что сервисный слой 2014 года спроектирован
  правильно.
* Два скорера капчи по цвету, включая меру совместимости градиентов Махаланобиса Галлагера.
* Набор тестов: статистики, эквивалентность кластеризации, совпадение быстрого скорера с эталонным,
  сборка пазла целиком и оба новых движка через модель скоупа.
* `.gitignore`, `.gitattributes`, `LICENSE`, `NOTICE` и эти документы.

# Архитектура

*[English version](architecture.md)*

Четыре слоя друг на друге: распознавание того, что на экране, воздействие на него, сервисный слой
выполнения скриптов и IDE для их написания.

## Распознавание элементов

**Элемент** — это шаблон: набор пикселей, у каждого цвет и смещение от начала координат элемента,
однажды снятый с экрана и сохранённый. Один такой шаблон хранит
`pixelbot.elements.ElementDescriptor`, коллекцию — `Elements`, а `ElemTools` читает и пишет архив
`elements.elz` рядом с программой.

Имена элементов иерархические, через точку, и это соглашение, а не то, что проверяется кодом —
например, `interface.buttons.close`. Скрипт спрашивает элемент по имени и получает его положение на
экране либо ничего.

Сопоставление — точное сравнение пикселей по снимку экрана, а не нечёткий поиск по картинке. Поэтому
шаблоны надо снимать с того же рендеринга, против которого они потом будут сопоставляться, и поэтому
инструменты для съёмки, проверки и пересъёмки (вкладка *Элементы*) занимают столько места. Взамен
получаем скорость и ноль ложных срабатываний.

У `ElementDescriptor` есть ещё тип цвета (`CT_MULTICOLOR` или упрощённый) и набор локалей, так что у
одного логического элемента могут быть варианты.

### Экран и ввод

`pixelbot.script.helper.RobotPeer` — обёртка над `java.awt.Robot`: снимает экран целиком или
прямоугольник из него в упакованный ARGB-массив, двигает и кликает мышью, нажимает клавиши.
`IOHelper` — фасад, который видят скрипты, и там же живут тайминги мыши: скорость перемещения,
длительность клика и паузы вокруг него рандомизируются в настраиваемых диапазонах — именно это
заставляет указатель вести себя не как машина.

`HighlightScreen` — прозрачное окно поверх всех, которое обводит найденные элементы рамкой. Это
отладочное средство, и именно из-за него программе нужна попиксельная прозрачность окон.

## Сервисный слой скриптов

То, вокруг чего проект на самом деле построен, и то, что лучше всего пережило десять лет. Выполнение
скрипта разбито на четыре независимые задачи, каждая — сервисный интерфейс, находимый через
`META-INF/services`:

```
script/parser/        исходник или архив  ->  то, что движок умеет выполнить
script/instantiator/  это самое           ->  выполнение и публикация определённого
script/scope/         объекты движка     <->  модель, независимая от движка
script/debuger/       пошаговое выполнение, точки останова
```

У каждой — пакет `general` с интерфейсами и по пакету на реализацию. Новый язык или новый движок —
это jar на classpath с регистратором в своём сервисном файле; в самой программе не меняется ничего.

### Парсеры

`IScriptParser` превращает файл в список `IScriptInstantiator`. Парсер объявляет тип файла, который
обрабатывает, идентификатор, отображаемое имя и приоритет; на один тип может претендовать несколько
парсеров — тогда вкладка настроек *Интерпретаторы* предлагает выбор, откуда и берётся список
JavaScript-движков.

| Парсер | Тип | Примечание |
| --- | --- | --- |
| `js.rhino`, debug | `djs` | Интерпретация, работает с пошаговым отладчиком |
| `js.rhino`, compile | `djs` | Компиляция в байткод, быстрее, без отладчика |
| `js.graal` | `djs` | Актуальный ECMAScript, выбор для нового кода |
| `js.nashorn` | `djs` | Самостоятельное продолжение движка из Java 8 |
| `java` | `djava` | Компилируется в процессе пакетным компилятором Eclipse |
| `jar`, `zip`, `clazz` | | Загрузка уже скомпилированного кода |

### Инстанциаторы

`ScriptInstantiatorManager` сопоставляет *класс* разобранного артефакта фабрике, которая умеет его
выполнить: `org.mozilla.javascript.Script` — фабрике Rhino, `org.graalvm.polyglot.Source` —
Graal-овской и так далее. Сопоставление идёт через `isAssignableFrom`, поэтому фабрика,
зарегистрированная на интерфейс, подхватывает любой конкретный тип, который выдал движок.

Инстанцировать скрипт — значит вычислить его и опубликовать определённые им глобальные объекты в
общий `GlobalScope`. Rhino делает это напрямую: ему передаётся живой `Scriptable`, который пишет
прямо в скоуп. У Graal и Nashorn свой глобальный объект, поэтому их фабрики после выполнения
копируют глобальные объекты — не данные, а ссылки, так что последующие изменения видны с обеих
сторон.

### Модель скоупа

Между движками и всем остальным лежит небольшая модель, которая ничего не знает о движках:

```
IScopeObject
  IScopeMap        объект с именованными членами
  IScopeList       массив
  IScopeFunction   вызываемое, с именами параметров
  IScopeString / IScopeNumber / IScopeBoolean / IScopeNative
```

Каждый бэкенд поставляет `IConverter`, работающий в обе стороны: объект движка в объект скоупа и
обратно во что-то, что движок примет. `JConverter` разбирается с тем, что везде одинаково —
строками, числами, булевыми, обычными Java-коллекциями и массивами, — а конвертер каждого движка
переопределяет своё.

Обратное направление, из модели скоупа *внутрь* движка, означает представить хостовый объект родным
для движка. Rhino получает реализации `Scriptable`, Graal — `ProxyObject` / `ProxyArray` /
`ProxyExecutable`, Nashorn — наследников `AbstractJSObject`. Именно поэтому дерево отладки, панели
параметров и список заданий работают одинаково, какой бы движок ни был выбран.

**Задание** обнаруживается через эту же модель: любой глобальный объект, который является map с
членом `main`, — это задание, и `GlobalScope.getJobs()` их находит. См.
[Написание скриптов](scripting.ru.md).

### Потоки

Скрипты выполняются в рабочем потоке, а GUI читает тот же скоуп из потока диспетчеризации событий.
Rhino и Nashorn это терпят. В контекст GraalJS одновременно может войти только один поток, и каждый
выданный `Value` привязан к контексту — поэтому `GraalRuntime` владеет контекстом и сериализует
любой доступ через один замок. Защищать нужно движок, а не данные, поэтому одного замка достаточно.

## Встроенная IDE

`pixelbot.components.editor` — текстовый редактор на Swing-овом `JEditorPane` с документом, который
ведёт лексер: `ScriptDocument` пересканирует изменённый абзац и применяет стили из `StyleProvider`.
Лексер — от Eclipse JDT: для Java по прямому назначению, для JavaScript — потому что грамматики
токенов пересекаются достаточно, чтобы раскрашивать (см. [заметки о переносе](migration.ru.md)).

Вокруг него: колонка номеров строк, она же поле точек останова (`JNumLinePanel`), инкрементальный
поиск, автодополнение по живому скоупу (`ScriptHint` обходит то же дерево `IScopeMap`, что показывает
отладочная панель), открытие файлов перетаскиванием и вкладки, отслеживающие несохранённые буферы.

Отладчик — Rhino-вский, обёрнутый так, что остальная программа об этом не знает: пуск, пауза,
продолжение, шаг внутрь, шаг через, шаг наружу, точки останова и дерево переменных, построенное по
модели скоупа.

Просмотрщик журнала (`pixelbot.components.logviewer`) читает ротируемый XML-журнал, который
программа пишет через `java.util.logging`. `BotLogger` перенаправляет туда же `System.out` и
`System.err` — поэтому вывод скрипта оказывается в том же окне, что и всё остальное.

## Приложение

`PixelBotApp` — загрузчик. Он строит classloader, покрывающий jar плюс каталоги `lib/` и `libext/`
рядом с ним, чтобы скомпилированные скрипты и дополнительные движки можно было положить рядом без
пересборки, и передаёт управление `Starter`, который выставляет look and feel и открывает
`PixelBotView`.

`PixelBotView` — главное окно: текущее задание и его вкл/выкл, полосы здоровья и маны, таблица
статистики событий и вкладки журнала и параметров задания. Из меню открываются панели настроек —
элементы, скрипты, интерпретаторы, тайминги ввода-вывода, — каждая из которых читает и пишет
настройки в узле `/pixelbot`. `FilePreferencesFactory` перенаправляет этот узел в файл
`pixelbot.fileprefs` в рабочем каталоге, поэтому конфигурация — это каталог, который можно
скопировать, а не что-то закопанное в реестре.
